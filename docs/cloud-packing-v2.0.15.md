# v2.0.15 투구 수·롤링 로그·저장 준비

## 사용자 측정과 원인 확인

v2.0.14 사용자 측정: 하루 3.0~3.3초, 저장준비 0.76~1.08초, 통신 두 번 모두 1.32초, 전송 1069~1353KB. 고정 선수 정보와 아마추어 gameLog 25조각이 매일 바뀌었다.

실제 앱 엔진을 3일 진행하고 선수 분리 결과의 base를 필드별로 비교했다. 대부분의 반복 변경은 profile.baseball.pitchMixSeason 및 pitchMixSeasonYear였다. 투구 수가 profile에 저장되어 있어 고정 정보와 함께 전송되고 있었다. 일부 구종/구속 발전 및 새 선수 초기화도 실제 변경으로 확인했으며 이들은 계속 저장한다.

게임 로그는 기존 엔진이 최대 600건을 유지하며 앞에서 오래된 항목을 제거한다. 순번 24개씩 나누면 앞쪽 삭제 때문에 나머지 모든 조각이 밀려 새 데이터처럼 전송된다.

## 변경

- 시즌 구종별 투구 수와 해당 연도를 일일 baseball 필드로 옮겨 고정 프로필 재전송을 줄인다. 전적·구종별 실제 투구 수 및 기존 데이터는 그대로 복원한다.
- 날짜 순서가 확인되는 gameLog는 날짜별 묶음으로 압축한다. 앞 날짜가 제거되어도 나머지 날짜의 키와 내용은 그대로 유지된다. 기존 엔진의 로그 유지 개수나 기록 내용은 변경하지 않는다. 같은 날이 24건을 넘으면 추가 조각을 만든다. 날짜 없는/정렬되지 않은 레거시 로그는 기존 순번 저장으로 보존한다.
- 선수 분리 시 전체 객체를 복사한 뒤 여러 필드를 delete하던 경로를 한 번 순회해 양쪽 객체를 구성하는 경로로 변경한다. 프로필/계약/알려지지 않은 추가 필드와 __proto__처럼 특수한 이름의 JSON 필드도 유지한다.
- 기존 저장 포맷은 계속 읽으며 새 날짜별 로그는 업데이트한 클라이언트에서 읽는다. 첫 새 형식 저장은 날짜별 로그를 한 번 이관한다. 매일 저장과 실패 복구/동시 수정 검증은 유지한다.

## 검증

3개 리그에 각각 600건 로그를 넣고 앞 12건 삭제/다음 날짜 12건 추가, 투구 수 갱신을 동일하게 수행했다. v2.0.14 PATCH 53,721바이트 대비 변경 후 8,251바이트였다. 날짜별 새 조각 3개만 전송되고 빠진 날짜 조각 3개가 unset된다. 전체 복원, 이전 저장 호환, 차가운 캐시 복원 후 재압축 0회, 누락/날짜 메타데이터 오류 거부, 순서 없는 레거시 로그와 특수 필드 보존을 확인했다.

실제 경기·아마추어·2군·육성·재정 일일 서비스를 실행해 만든 동일한 3일치 상태를 사용한 로컬 Node v24 비교다. 네트워크나 사용자 저장을 사용하지 않았으며 초기 시즌 상태이므로 장기 저장/사용자 기기 성능에 그대로 적용할 수 없다.

3일 합계 준비·비교 시간 약 40%, 전송량 약 43% 감소. 개별 날짜에는 형식/메타데이터 비용으로 전송량이 늘어날 수 있다. 전체 하루 진행 시간의 감소율이 아니다.

재현: BASEBALL_PREVIOUS_CLOUD에 v2.0.14 cloud-only.js 경로를 지정하고 node tests/cloud-packing.benchmark.cjs. 전송/복원 회귀는 tests/cloud-rolling-log.test.cjs 및 기존 저장 실패/응답 유실/충돌/실제 다음 경기일 동일성 검사로 확인한다. 전체 회귀와 720경기 검사도 수행한다.

통신 시간에는 업로드와 서버 응답 대기가 포함된다. Server-Timing이 제공되지 않고 현재 저장소에 백엔드 구현이 없어 1.32초의 세부 원인은 확정하지 못했다. 복구용 백업은 유지한다. 실제 기기에서 배포 후 전체 시간을 다시 측정해야 한다.
