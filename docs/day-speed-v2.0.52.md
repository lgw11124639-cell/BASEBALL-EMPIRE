# 2.0.52 하루 진행 속도 개선

## 변경

홈의 수동 하루 진행은 날짜를 저장한 다음 해당 날짜의 경기를 준비하며 다시 저장하던 두 작업을 하나의 원자적 처리로 묶는다. 같은 최종 날짜·경기·관전 완료 표시를 한 번 저장한다. 날짜 이동은 여전히 하루이며 자동 진행도 매일 저장한다. 별도 관전 준비와 연도 전환의 기존 경로는 유지한다. 경기 준비·저장 실패 시 클릭 전 상태로 돌아가고, 실제 경기를 만들지 못했다면 완료 표시를 남기지 않는다. 저장을 백그라운드로 미루거나 경기·육성 결과를 생략하지 않는다.

단일 시즌 신기록 확인은 선수마다 전체 박스스코어를 재검색하던 작업을 한 번의 집계로 바꾼다. 선수 ID 맵, 실제 박스 기록·이름·시즌·출전 자격 검증을 사용한다. 투수의 타격용 잔여 필드나 타자의 투수용 잔여 필드가 신기록으로 잘못 쓰이지 않도록 한다.

클라우드 저장은 현재 시즌 전체를 먼저 JSON화한 뒤 조각별로 다시 직렬화하던 중복 작업을 제거한다. 독립된 선수·아마추어·리그·시즌 기록 준비를 겹쳐 수행하고 기존 gzip 동시 작업 수 제한을 유지한다. 한 저장 내 객체 JSON을 변경 비교·크기 계산·진단에 재사용하며, 비교 기준은 서버 승인 후 분리한 스냅샷에만 보관한다. 로그인·기준 교체 시 캐시를 비운다. 과거 시즌의 실제 수정·삭제도 매번 정확히 감지한다. 서버 저장 형식, PATCH/PUT, 충돌 검사, 응답 유실 복구와 압축 해제는 그대로다.

## 측정

벤치마크는 사용자 저장이나 실제 서버를 사용하지 않는다. 프로덕션 엔진과 저장 코덱, 번들 fflate를 사용하고 실제 생성 경기에서 복제한 300경기·720선수·약31MB의 합성 저장을 비교했다. 기존/새 버전의 순서를 바꾸어 두 번씩 실행했다. 통신 지연은 제외한 로컬 처리 시간이며 사용자 기기의 예측값이 아니다.

| 상황 | 기존 | 변경 | 저장 요청 |
| --- | --- | --- | --- |
| 홈에서 당일 경기 준비가 끝난 일반 클릭 | 2.35–2.51초 | 1.70–1.75초 | 2 → 1 |
| 아직 당일 준비가 없는 상태에서 진행 | 3.79–4.20초 | 2.55–2.72초 | 2 → 1 |

일반 클릭의 평균 로컬 시간은 약29%, 준비 전 상태는 약34% 감소했다. 실제 체감에서는 통신 왕복도 한 번 줄어든다. 준비 전 시험의 PATCH JSON 합계는 1,983,681 → 1,170,961바이트로 약41% 감소했다. 일반 클릭은 첫 저장이 날짜 중심의 작은 변경분이므로 JSON 총량 감소는 작다. 이 수치는 HTTP 본문 gzip 전 JSON 크기이며 실제 네트워크 전송량과 구분한다.

별도 신기록 확인 시험은 합성 720경기에서 314.1 → 12.3ms였다. 실제 12일·50경기 시뮬레이션은 해당 집계 수정만으로 14.25 → 13.31초였다. 전체 게임 상태 해시와 기록·기사 해시가 이전 코드와 일치했다.

재현:

- BASEBALL_PREVIOUS_APP=/path/to/previous-app.js BASEBALL_PREVIOUS_CLOUD=/path/to/previous-cloud.js BENCH_GAMES=300 DAY_CLOUD_BENCH_REPORT=report.json node tests/day-cloud-performance.benchmark.cjs
- 준비 전 상황은 BENCH_PREPARED_HOME=0 추가
- BASEBALL_PREVIOUS_APP=/path/to/previous-app.js node tests/single-season-records.benchmark.cjs

원자료: day-cloud-optimization-v2.0.52.json, day-cloud-unprepared-v2.0.52.json, records-optimization-benchmark.json, records-day-optimization-benchmark.json.

## 검증과 한계

실제 엔진으로 기존/변경 경로의 전체 상태를 비교했다. 정상 클릭, 월말, 포스트시즌, 다음 클릭 날짜, 저장 실패, 경기 준비 실패, 결과 없는 준비의 복구를 검사한다. 클라우드 wire를 복원한 전체 상태도 대조한다. PC·모바일 실제 홈 버튼에서 요청 횟수·관전 준비·실패 복구를 확인한다. 오래된 시즌 수정·필드 삭제·기준 교체·저장 실패·리비전 충돌·압축 실패 회귀 검사를 유지한다.

서버 응답 시간, 기기 성능, 시즌 초기 자료 생성과 오래된 저장의 첫 변환 비용은 남는다. 기록이나 복구용 데이터를 버리는 방식의 속도 개선은 하지 않는다.
