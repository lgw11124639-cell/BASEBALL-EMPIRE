# v2.0.8 저장 전송량 개선

사용자 화면의 실제 진단값은 하루 2.7초, 저장 2.0초, 요청 약 523KB였으며 `trainingReports`가 약 241KB였다. 이 화면에서는 경기 계산보다 저장이 큰 비중을 차지했다.

원인: `trainingReports`는 날짜/구단 키의 객체지만 `shardArrayFields`에만 등록되어 있었다. 배열 검사에서 제외되고 보조 압축 목록에도 없어서 매일 객체 전체를 JSON으로 다시 전송했다.

기존 `packAuxiliaryFields` / `unpackAuxiliaryFields`의 지원 목록에 연결했다. 저장 직렬화 시 gzip/base64 문자열로 압축하고 불러올 때 원래 객체로 복원한다. live 게임 상태는 바꾸지 않는다. HTTP `Content-Encoding`은 사용하지 않으므로 기존에 관측된 CORS 문제를 우회하려고 TLS나 검증을 해제하지 않는다.

원래 JSON 객체 저장, 예전 보조 gzip 봉투, 배열 형태 자료도 최신 클라이언트에서 읽을 수 있다. 보고서 항목을 삭제·요약하거나 저장/변경 비교/리비전 검사를 생략하지 않는다. 원시 필드에서 압축 필드로 이전하는 변경은 기존 PATCH의 set/unset으로 원자적으로 전달한다. 압축을 지원하지 않는 실행 환경은 기존 원시 저장 방식으로 돌아간다. 새 압축 필드를 읽으려면 사용하는 기기를 최신 앱으로 새로고침해야 한다. 구버전 클라이언트의 새 형식 읽기를 보장하는 변경은 아니다.

안전성 보완: 기존 전체 PUT 경로도 변경분 PATCH와 같은 guarded upload를 사용한다. 성공 응답이 유실되면 서버의 리비전과 정확한 packed snapshot을 비교해 이미 반영된 경우 재전송하지 않는다. 서버 오류나 충돌을 성공으로 처리하지 않고, 확인된 응답이 오기 전에는 acknowledged baseline을 갱신하지 않는다.

## 검증

합성 보고서 3,500건: 해당 필드 270,485 bytes → 31,146 bytes, 약 88.5% 감소. 사용자 저장을 직접 읽어 측정한 값은 아니며 전체 요청 523KB가 같은 비율로 줄거나 실제 2.7초가 특정 시간으로 줄었다고 주장하지 않는다. 실제 서버 지연은 업데이트 후 측정이 필요하다.

`tests/cloud-training-reports.test.cjs`는 다음을 실제 압축/복원 및 저장 함수로 검증한다.

- 보고서 전체와 관계없는 계약/문자열 자료의 무손실 복원, live state 불변.
- 기존 원시 저장/이전 gzip 봉투 읽기, 압축 미지원 환경의 fallback.
- 같은 객체 내부 변경 시 캐시 무효화, 손상된 gzip의 명시적 실패.
- 원시 필드 삭제와 압축 필드 추가가 동일 delta에 포함됨.
- 변경 없는 다른 필드는 PATCH에서 제외됨.
- 통제된 서버의 저장 실패 때 기준 snapshot 유지 및 재시도 후 전체 복원.
- PATCH와 PUT 모두 서버 반영 후 응답이 끊긴 경우 한 번만 저장됨.

사용자 계정이나 실제 클라우드 저장에 접속/수정하지 않고 인메모리 서버 fixture를 사용했다. 서버 API와 저장 스키마 버전, 자동 저장 주기는 변경하지 않았다.
