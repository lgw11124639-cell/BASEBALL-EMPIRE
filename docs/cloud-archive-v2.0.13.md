# v2.0.13 변동 기록 분할과 로드 캐시

사용자 측정: 하루 7.1초, 저장 6.3초, 통신 2.80초, PATCH 4096KB, 전체 26336KB. clubTransactionArchive가 1811KB를 차지했다. 기존 shardArrayFields 설정은 배열에만 적용되므로 실제 연도별 객체인 이 필드는 통째로 전송되고 있었다. '직렬화/압축' 기존 표시는 HTTP 호출 내 비용이고 전체 archive packing 시간을 포함하지 않았다.

## 변경

- clubTransactionArchive 연도별 배열을 20개 기록씩 gzip 조각으로 저장한다. 기존 beShardManifest에 kind:yearArrays 메타데이터를 사용하고 동일한 revision-checked PATCH에서 manifest/조각/기존 raw 필드 삭제를 함께 전송한다. 신규 추가가 발생하면 해당 연도의 꼬리 조각과 길이 메타데이터만 변경된다. 과거 수정도 매번 정확한 JSON 비교로 감지하며, 아무 기록도 삭제하거나 요약하지 않는다.
- 정상 연도별 배열 이외의 레거시 객체 형태는 통째 gzip으로 보존한다. 이전 raw 객체와 배열 저장도 계속 읽는다. 조각 누락/길이 오류는 실패로 처리한다. 새 포맷을 읽으려면 업데이트한 클라이언트를 사용한다.
- 저장 불러오기 때 해제한 JSON 원문과 서버의 원래 gzip 문자열을 캐시에 등록한다. 기존 배열, 리그, 아마추어 경력, 보조 archive, 새 변동 기록 모두 적용한다. 재직렬화한 내용이 정확히 같을 때만 기존 바이트를 재사용하므로 in-place 변경을 누락하지 않는다. 캐시는 메모리에만 존재한다.
- 사용자 화면에 전체 저장준비 및 저장 후 처리 시간을 추가한다. 리그의 '변경'은 실제 PATCH 필드 수와 다르게 압축 캐시 miss를 세던 값이므로 '압축 갱신'으로 명확히 표시한다. 실제 전송량/변경 필드는 기존 PATCH 진단으로 확인한다.

## 검증과 한계

합성 변동 기록 9개 연도 3,600건에 새 기록 1건을 추가했다. 원본 객체 1,379,228바이트 대비 해당 archive 추가 PATCH는 manifest를 포함해 771바이트였다. 전체 사용자 저장의 감소율 또는 실제 통신 시간 측정은 아니다. 첫 새 포맷 이관에는 기존 archive의 압축 조각 전체를 한 번 전송한다.

전체 기록 복원, 원본 불변성, 과거 in-place 정정, 새 기록 한 조각 전송, cold-load 후 동일 데이터의 압축 작업 0회, 기존 raw/배열/비표준 객체 호환, 누락/길이 오류를 검사했다. 기존 실제 cloudSave의 실패/재시도/응답 유실/409 충돌 검사에도 연도별 변동 기록을 포함했다. 매일 저장과 동시 수정 검증은 계속 수행한다. 사용자 계정/클라우드 원본을 읽거나 쓰지 않았다.

실제 사용자 기기의 하루 시간은 배포 후 재측정이 필요하다. 서버 응답 지연이나 전체 시즌 데이터 직렬화 비용이 모두 제거되는 변경은 아니다.
