# v2.0.14 일일 변동과 과거 기록의 분리

사용자 측정은 하루 3.0~3.4초, 저장 2.2~2.4초, 저장준비 0.79~0.89초, 통신 1.35~1.42초, PATCH 2243~2810KB였다. 선수 묶음이 1151~1422KB, 리그 618~653KB, 아마추어 경력이 422KB를 차지했다. 드래프트 기록 249KB가 원본 필드로 전송되는 경우도 있었다.

## 변경

- 프로 선수는 전적/현재 2군 성적/피로/부상 같은 일일 필드와 프로필/계약/이력 같은 나머지 필드를 분리해서 압축한다. 프로 선수 묶음은 8명으로 나눠 한 선수의 성장/계약 변경이 주변 31명 이력의 재전송으로 이어지지 않게 한다. 아마추어 리그의 players/prospects에도 같은 분리를 적용한다.
- 이름, 계약, 성장 이력, 구종, 알려지지 않은 추가 필드는 모두 보존한다. 분리할 필드를 따로 지정할 뿐 필드를 버리지 않으며 모든 묶음을 매번 정확한 JSON으로 비교한다. 기량/구종/과거 정보의 in-place 변경도 저장한다. 선수 배열 순서와 중첩 데이터의 JSON 값은 동일하게 복원한다.
- 아마추어 경력은 연도와 안정적인 ID 버킷으로 나눈다. 올해 성적 갱신이 완료된 과거 시즌 경력을 함께 전송하지 않는다. 경력 행의 원래 인덱스를 저장해 정렬되지 않은 경력, 같은 연도에 여러 기록이 있는 경우, 빈 경력도 정확히 복원한다. 비표준 레거시 형태는 기존 전체 버킷 경로로 보존한다.
- draftResults를 보조 gzip 필드에 포함한다. HTTP Content-Encoding이나 서버 API 변경 없이 기존 revision-checked PATCH를 사용한다.
- 화면의 저장 상위 set 크기가 첫 요청 샘플로 고정되던 문제를 수정한다. 이미 만들어 둔 요청 JSON 길이에서 계산해 매 요청 갱신하며, 큰 set 객체를 한 번 더 직렬화하지 않는다.

첫 저장은 기존 분할 필드에서 새 분할 필드로 이관하므로 전체 새 묶음을 한 번 전송한다. 이후 일일 PATCH에서 반복 전송을 줄인다. 기존 raw/배열 조각, 이전 아마추어 경력 v1, 통째 gzip 저장을 읽을 수 있다. 새 형식은 업데이트된 클라이언트로 읽어야 한다. 매일 저장, 실패 시 중단/복구, If-Match 충돌 검증은 유지한다. 게임 엔진과 경기 횟수/훈련/재정 처리는 변경하지 않는다.

## 검증

합성 자료: 프로 320명, 아마추어 선수 96명, 경력 1,200명×6개 연도, 드래프트 110명 및 프로필/과거 이력. 같은 자료의 모든 선수 일일 기록/피로/부상과 올해 경력, 드래프트 관찰문을 동일하게 수정하여 v2.0.13과 비교했다.

| 측정 | 일일 PATCH |
|---|---:|
| v2.0.13 | 462,994바이트 |
| v2.0.14 | 30,981바이트 |

이 합성 자료의 감소율은 약 93.31%이며 실제 사용자 저장의 감소율이나 전체 하루 시간 측정이 아니다. 최종 프로필/아마추어 경력/경기 기록을 모두 복원하여 비교했다. 변경되지 않은 base 및 과거 연도 조각이 PATCH에 포함되지 않는지, 과거 프로필 정정은 감지하는지, 새 접속 캐시 재사용, 기록 누락 거부, 비표준 데이터 보존을 검증했다.

실제 앱 엔진으로 하루를 진행한 상태를 새 저장 형식으로 복원한 뒤, 원본과 복원본에서 각각 다음 하루를 진행했다. 전체 상태를 정규화해 비교했으며 경기 결과, 재정, 성장과 기타 상태가 일치했다. 실제 cloudSave의 실패/재시도/응답 유실/409 충돌 시험에도 선수/올해 경력 변동을 포함했다. 기존 전체 회귀와 720경기 검사도 통과했다.

실행: node tests/cloud-player-split.test.cjs. 선택적으로 BASEBALL_PREVIOUS_CLOUD 환경 변수에 v2.0.13 cloud-only.js 경로를 지정하면 같은 합성 자료의 전송량을 비교한다. 사용자 계정이나 실제 클라우드 저장 원본은 읽거나 쓰지 않았다.
